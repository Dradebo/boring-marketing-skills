## Case A — DHIS2 Tracker assessment to PDF

- **Public source:** https://community.dhis2.org/t/pdf-report-out-of-tracker-data/72453
- **Observed:** 18 May 2026 discussion: practitioner wants an automated PDF from a completed Tracker assessment within DHIS2 and reports a Report Builder error. Reply asks for DHIS2/app version, failure details and reproduction steps; whether issue was solved remains **unverified** as of this dry run.
- **Stash:** https://github.com/Dradebo/Report-builder. Existing Fly Fisher code notes mention `printReportAsPDF`, browser print behavior, a tenant-specific endpoint and significant integration/security uncertainty. This run did **not** execute the app or inspect its current source.
- **Decision:** **HOLD (technical validation candidate, not yet a buyer)**. This is an appropriate useful topic but not a proven unmet commercial need. First validate whether existing app functionality resolves the error, then reproduce in safe dummy data on a version-matched test instance. Without version/error information, do not promise a fix.
- **Marketing skill test:** `audience-research` should identify the exact task and unresolved status; `pitch-the-fix` must refuse to assert that the company is losing revenue, or that a paying client exists; `performance-review` has zero performance events and must write no positive learning.
- **Acceptable draft help (not sent):** “I saw your Tracker-to-PDF question and the follow-up asking for the app version and error. If this is still open, could you share the DHIS2 version and error steps? I can try reproducing with synthetic Tracker data and share the result. An existing Report Builder may already be sufficient.”
- **Next decision (10–20 min):** verify latest thread replies and existing WCA app/documentation; identify version-specific reproduction requirement. If already solved, **KILL/ARCHIVE**.

## Case B — WhatsApp/Instagram follow-up tracking

- **Public source:** https://www.reddit.com/r/smallbusinessowner/comments/1twby2k/i_spent_20_minutes_explaining_my_services_to_a/
- **Observed:** Original June 2026 complaint about lost status across conversations. Replies recommended native WhatsApp Business labels. A July 2026 follow-up reports labels plus spreadsheet helped somewhat, but data entry felt burdensome; the author also discloses involvement in a lightweight tracker. This is mixed evidence, **not** proof the same individual wants our product.
- **Existing solutions:** native labels, lightweight stage list, possible manual spreadsheet. Do not assert that WhatsApp labels solve all cross-platform reconciliation, nor claim bespoke CRM is required.
- **Decision:** **HOLD / NO BUILD** until direct evidence of an unsolved task, recurring cost, reachable authorized buyer and whether manual/native tools are insufficient. This is a contrast/control pond, not an additional active product line.
- **Marketing skill test:** `find-local-clients` must not fabricate Ugandan businesses or assert this Reddit thread concerns Uganda. `pitch-the-fix` should recommend a five-status visual workflow as a helpful artifact before any paid integration. `performance-review` must not infer a conversion.
- **Acceptable internal help artifact (not sent):** five statuses: new → quoted → deciding → ordered / inactive; optional date of last follow-up; explicit test of whether this adds value over labels and whether cross-channel reconciliation is the genuine problem.
- **Next decision:** validate the user workflow in a consensual test with an actual local business **only if a suitable contact and expressed need exist**; otherwise **ARCHIVE**.
